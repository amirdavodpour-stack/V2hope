# Internationalization (ARB + flutter gen-l10n)

## What's here
- `l10n.yaml` -- config for `flutter gen-l10n`.
- `lib/l10n/app_fa.arb` -- the Persian template (source of truth: this is
  the file you edit to add/change strings). Every key has an `@key`
  metadata block with a `description` for translators.
- `lib/l10n/app_en.arb` -- English translation, mirroring the same keys.
- `pubspec.yaml` has `flutter: generate: true`, which makes Flutter run
  `gen-l10n` automatically on every `flutter pub get` / `flutter run` /
  `flutter build` -- you never invoke the generator by hand.
- `lib/main.dart` wires `AppLocalizations.delegate` into `MaterialApp`.
- `lib/features/auth/login_page.dart` is fully migrated as the reference
  example -- every hardcoded Persian string on that page now comes from
  `AppLocalizations.of(context)!.someKey` instead.

## IMPORTANT: one step you must run locally
This sandbox has no Flutter toolchain, so **`AppLocalizations` has never
actually been generated here** -- `import 'package:flutter_gen/gen_l10n/app_localizations.dart'`
will not resolve until you run, once, locally:
```
flutter pub get
```
(`generate: true` makes this also run `gen-l10n` and produce the class.)
Until then, any file importing `AppLocalizations` -- currently `main.dart`
and `login_page.dart` -- will not compile. This is expected, standard
Flutter behavior (the generated class is intentionally not committed), not
a bug in this change. Run `flutter pub get && flutter analyze` before
anything else.

## Why only one page was migrated
The other ~14 pages still have their Persian strings hardcoded. Migrating
all of them in one pass, with no Flutter toolchain available to verify
compilation, would be a large, unverified change across the entire UI --
exactly the kind of high-risk change to avoid making blind. `login_page.dart`
demonstrates the complete pattern end-to-end (string extraction, ARB
metadata, English translation, `l10n.of(context)!` usage including inside
an `async` method, migrating a dynamic/ternary string). Extend the same
pattern to the rest, verifying with `flutter analyze` as you go.

## Checklist for migrating another page
1. Find every hardcoded Persian (or English) string literal in the file.
2. Add each as a new key to `lib/l10n/app_fa.arb`, with an `@key`
   description. Reuse an existing key (e.g. `backButtonTooltip`,
   `emailLabel`, `passwordLabel`) instead of creating a duplicate wherever
   the same string already appears in another migrated page.
3. Add the matching English value to `lib/l10n/app_en.arb` (same key).
4. In the widget file: `import 'package:flutter_gen/gen_l10n/app_localizations.dart';`
5. Inside `build()` (or any method with a `BuildContext`): grab
   `final l10n = AppLocalizations.of(context)!;` once at the top, then
   replace each literal with `l10n.yourKey`.
6. For strings used inside an `async` method (like `submit()` in
   `login_page.dart`): grab `l10n` at the very start, *before* the first
   `await` -- using `context` after an `await` without checking `mounted`
   first is a real Flutter pitfall (`use_build_context_synchronously`).
7. Run `flutter analyze` -- it will catch unused imports, missing keys, and
   ARB/Dart mismatches immediately.
8. Once every page is migrated, the ~9 files that manually wrap themselves
   in `Directionality(textDirection: TextDirection.rtl, ...)` (a workaround
   from before locale support existed -- see the review note in `main.dart`)
   can have that wrapper safely removed, since `locale: Locale('fa')` on
   `MaterialApp` now makes RTL the ambient direction app-wide. Do this only
   after confirming with `flutter analyze` + a real device/emulator run,
   since removing it is exactly the kind of change this project has learned
   to be careful with when unverified.

## Adding a new locale later
Add `lib/l10n/app_XX.arb` with the same keys, add `Locale('XX')` to
`supportedLocales` in `main.dart`. No other wiring needed --
`flutter gen-l10n` picks up any ARB file in `arb-dir` automatically.
